# Implementation Backlog

Phased by dependency, not by "importance" — Phase 2 has to happen first regardless of which clinical module the business wants soonest, because nothing clinical is safe to expose without it. Within a phase, items are roughly build-order too.

A module is not "done" per this backlog until: models + migrations, DRF ViewSets/serializers (role-gated per `03-rbac-and-roles.md`), the relevant role template(s), audit wiring (`07-audit-and-security.md`), any domain events it emits/consumes (`05-integration-architecture.md`), tests (unit + tenant-isolation, matching the existing test culture — see `apps/tpa/tests.py`'s isolation tests as the pattern to copy), and frontend screens. "Basic screens exist" is not done — matches your spec's closing instruction exactly.

## Phase 5 — Diagnostics & Pharmacy — SHIPPED

21. ~~`laboratory` app~~ — done: `LabTest`, `LabTestPackage`, `LabOrder`, `SampleCollection`, `LabResult` (`TenantScopedModel, FinalizableModel`). **Shipped correction**: no separate `verify_labresult` + `finalize_labresult` pair as originally sketched — "verify" (the lab-industry term for pathologist sign-off) and "finalize" (this codebase's generic lock-against-edits term) are the same transition, collapsed into one `FinalizableModel.finalize()` call exposed via a `verify` action/`laboratory.verify_labresult` permission. `laboratory.result_critical` is a real signal, fired from `LabResultViewSet.perform_create`/`perform_update` when a result's flag is `critical`, consumed by a new `apps.automation` receiver that creates an urgent (`due_at` = +1h) follow-up `Task` — the same domain-event pattern as Phase 1's `appointment_no_show` → recall task.
22. ~~`radiology` app~~ — done: `RadiologyProcedure`, `RadiologyOrder`, `RadiologyReport` (same verify/finalize collapse as `LabResult`). **Shipped correction**: a single `image_file` FileField, not the originally-sketched multi-image attachment — a full multi-image study would need a child model, out of scope for what this system needs beyond attaching the report's key image; reuses `apps.patients`' upload validators (`ALLOWED_DOCUMENT_EXTENSIONS`, `validate_document_size`) rather than redefining them.
23. ~~`pharmacy` app~~ — done: `Medicine`, `MedicineBatch`, `DispenseRecord`, `StockAdjustment`, plus a deliberately minimal `Supplier` (documented in its own docstring as to-be-migrated onto Phase 7's `inventory.Supplier`, not extended in place). `dispense_medicine`/`adjust_stock` in `apps/pharmacy/services.py` are `select_for_update()`-locked against `MedicineBatch.quantity_available` — same race-safety pattern as `apps.appointments.services.book_appointment` and Phase 4's `admit_patient`. `DispenseRecordViewSet`/`StockAdjustmentViewSet` return 409 (not 500) on `InsufficientStock`.
24. ~~Role templates: `lab_technician`, `lab_manager`, `radiology_technician`, `radiologist`, `pharmacist`~~ — done. Technicians get `["view", "add", "change"]` on their app but not the `verify_*` permission (they enter results/reports; pathologist/radiologist verify); `lab_manager`/`radiologist` get the verify grant via a new shared `DIAGNOSTIC_VERIFY_PERMISSIONS` list (kept separate from `CLINICAL_FINALIZE_PERMISSIONS` since lab/radiology verification is a pathologist/radiologist-specific act, not something `doctor`'s template also gets). `owner`/`admin` extended with both new permissions and all three new apps added to `FULL_ACCESS_APPS`.
25. ~~Frontend: lab order/result screens, radiology worklist, pharmacy dispensing screen~~ — done, shipped as one combined **Diagnostics** screen (`DiagnosticsPage.tsx`, lab/radiology tabs sharing one "which patient" order-creation flow — order→result/report→verify is the same shape in both) rather than two near-identical routes, plus a separate **Pharmacy** screen (`PharmacyPage.tsx`: catalogue with low-stock flagging, dispense-against-a-batch modal, recent-dispensing feed). New `erpNav` entries gated on `laboratory.view_laborder`/`pharmacy.view_medicine`.
26. ~~ERP ops dashboard: + lab TAT, pharmacy low-stock~~ — done: `GET /api/v1/reports/lab-tat/` (orders today, pending-order count, average order→verified-result turnaround in minutes) and `GET /api/v1/reports/pharmacy-low-stock/` (medicines at/below `reorder_level`, top 10 by scarcity), each a new dashboard stat row gated on any `laboratory.*`/`pharmacy.*` permission — same pattern as Phase 4's bed-occupancy row.

**Exit criterion — met:** an OPD/IPD encounter can be sent for lab and radiology investigations, results/reports entered and verify-locked against further edits (`test_verify_locks_result_against_further_edits_and_marks_order_verified`, `test_verify_locks_report_against_further_edits`), a critical lab value fires a real urgent-task alert (`test_critical_lab_result_creates_urgent_automation_task`), and a prescription can be dispensed against batch stock with a race-safe, 409-on-insufficient-stock decrement (`test_dispense_record_api_returns_409_on_insufficient_stock`). RBAC follows the established pattern: whole-ViewSet `RequiresClinicalDetailPermission` gate on order/result/report/dispense content, catalogue data (`LabTest`, `RadiologyProcedure`, `Medicine`) deliberately ungated for front-desk/billing visibility, technician-vs-verifier separation enforced at the permission layer, not just the UI (`test_lab_technician_can_enter_results_but_cannot_verify` gets a real 403).

Full backend suite: 34 new tests this phase (30 in `apps/laboratory`/`apps/radiology`/`apps/pharmacy` covering lifecycle, verify-locking, RBAC, tenant isolation, and the critical-result signal; 4 new in `apps/analytics` for the two dashboard snapshots), all passing. Total suite 530 passing (up from 488 at the end of Phase 4) — the remainder of that delta is externally-scaffolded Phase 6/7/8 content (`emergency`/`ot`/`icu`/`bloodbank`/`finance`/`hr`) that landed in the working tree during this phase but is not part of Phase 5's own scope or exit criterion; two of its bugs were fixed only because they blocked this phase's own `manage.py check`/test collection (a premature `ipd.Admission.source_ed_visit` FK reference before `emergency` was registered, a `VentilatorLog.settings` field shadowing `django.conf.settings`, and missing `__init__.py` in `apps/finance`/`apps/hr` that broke pytest collection for the whole suite) — that content is otherwise untouched and unreviewed by this phase's work. Same 2 pre-existing, unrelated Postgres-only trigger failures under local SQLite as every prior phase, plus 1 pre-existing RBAC-template test (`test_hospital_administrator_template_grants_facilities_but_not_clinical_detail`) that now conflicts with an `access_clinical_detail` grant added to `hospital_administrator` by that same external content — also out of this phase's scope to fix. Full frontend suite green (24 tests, no new component tests — same documented gap as `ConsultationPanel`/`AdmissionDetailPanel` in Phases 3–4), clean typecheck.

## Explicitly out of scope for this backlog

- Full double-entry accounting / statutory financial compliance (flagged in `02-domain-model.md`) — integrate with dedicated accounting software instead if needed.
- A dedicated informed-consent management system beyond the placeholder noted in `07-audit-and-security.md` §2c.
- Splitting CRM and ERP into separately deployed services — the event-based boundary (`05-integration-architecture.md`) makes this possible later; nothing here does it now, because nothing in the stated goal ("small hospital initially, multi-branch later") requires it yet.
